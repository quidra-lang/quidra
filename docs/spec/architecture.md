# Quidra Architecture

Quidra optimizes for semantic density, static verifiability, human readability, and LLM generation and repair.

## Compilation

The C++20 compiler lexes indentation-aware source into tokens, builds a parsed AST, resolves modules, monomorphizes generics into a concrete program, checks types/definite initialization/storage effects, resolves call semantics, lowers the checked program to typed Quidra IR, and emits LLVM IR. Clang produces the native executable. Source programs execute as native code.

Language semantics belong to the frontend. LLVM is an implementation target. Typed IR separates semantic checks from native representation and supports source inspection, transformations, and future backend work.

### Phase ownership and lowering invariants

The compiler keeps semantic ownership directional. Parsing owns syntax shape; resolution and checking own names, concrete types, authority, initialization, effects, numeric representation, and operator validity; typed IR carries those decisions forward; LLVM lowering consumes them rather than re-inferring source intent. Shared operator classification is centralized so checker, IR lowering, and native lowering cannot silently evolve different operator categories.

Native lowering may change representation only when the change is unobservable under the checked language contract. Function-frame scratch storage is planned before basic-block emission and allocated in the entry frame when an IR operation needs temporary native storage. A source loop must not accumulate native stack space merely because an instruction inside the loop needs scratch memory. Block emission reuses the preplanned slot; runtime-sized semantic data uses the managed/runtime allocation model instead of an unbounded sequence of loop-local LLVM `alloca` operations.

This phase boundary is a correctness property, not only an optimization. Backend transformations may erase proven checks or choose cheaper storage, but they may not recover missing semantic facts by guessing from source spellings, LLVM pointer shapes, or incidental control-flow layout.

## Core contracts

- Reserved identifiers are absolute in user code: a reserved spelling cannot be redefined as a binding, parameter, function, class, field, method, generic parameter, binder, CLI field, or import alias, even behind qualification. Standard namespaces are always visible and are not imported or aliased; only referenced standard implementations are linked. Standard-library internal generated declarations are language-owned and are the implementation-level exception.
- File-aware compilation resolves source/package imports before ordinary semantic checking. Import aliases become explicit namespaces; nested source modules are flattened to unique internal names while source-facing qualification remains alias-based.
- Unquoted non-standard targets resolve installed packages through configured package paths and never fall back to a same-named file in the working directory. Quoted relative imports use the importer directory and quoted `@/` imports use the command working directory. Import cycles are rejected.
- Generic classes, functions, and methods are monomorphized before ordinary checking. Concrete type tuples receive deterministic internal names, repeated tuples reuse instances, and generic bodies are checked after substitution.
- Function boundaries have explicit static types; local inference uses `auto`.
- Four-space indentation defines block structure.
- Ordinary `=` has observable independent value semantics for arrays, bin, classes, and other values. The backend may share storage, use copy-on-write, elide copies, or move values when that is unobservable. Class copies preserve per-field initialization state; immutable strings may share backing text directly. Managed strings may lazily cache byte length and a forward code-point cursor; this preserves Unicode code-point semantics while avoiding repeated prefix rescans and a retained full offset table.
- `&storage` forms a safe abstract storage address. Local `T &alias = &storage` bindings provide read/write access and may be rebound with `&alias = &other`; `const T &view = &storage` provides a live read-only path that cannot be rebound or promoted back to `T &`. `const T` is an immutable initialized value binding. Const is path-local: another writable alias may still change the underlying storage. References can target bindings, fields, array elements and bin elements without exposing raw pointer arithmetic or a dereference operator.
- Address formation is not a value read. Reference-parameter and method effects track read-before-write requirements and definite initialization. Read-only `const T &` parameters require initialized storage and cannot contribute write/initialize/invalidate effects.
- References to substorage keep the captured backing storage alive if the containing binding is later replaced.
- Fixed array lengths belong to types; dynamic lengths are runtime data. Consecutive fixed dimensions are a representation optimization boundary: the LLVM backend stores eligible fixed runs as one headerless row-major block, so `int[5][7][]` uses the physical equivalent of 35 contiguous `int[]` slots while the source type remains `int[5][7][]`. A dynamic `[]` stops that flattening run. When a fixed shape is widened to a compatible dynamic shape, typed IR materializes the required dynamic representation recursively rather than reinterpreting incompatible storage. If a reference targets an intermediate fixed-array element, the affected fixed edge remains boxed so reference behavior stays observable-identical, including for `const T &` paths. `bin` stores a bit length followed by packed payload bytes; source indexing addresses bits, not byte elements.
- `array(n)` and uninitialized fixed arrays allocate storage immediately while initialization is tracked independently per leaf element. The managed allocation registry carries a compact initialization bitmap until the allocation becomes fully initialized. Reads validate this state; stored zero bits are never used as an initialization sentinel.
- `tensor<T>` is a dedicated dense numeric type with shape/stride/offset descriptors and shared backing storage. The element dtype is mandatory and static. Source types may optionally add an exact-rank pattern as `tensor<T><D0, D1, ...>`; each axis is a nonnegative extent or `_` wildcard, and the pattern length is the required rank. Dtype and shape therefore occupy separate syntax groups. `neural` shares the same shape-pattern semantics, with `neural<D...>` shorthand for `neural<float32><D...>`. Additional rank/shape facts are inferred flow-sensitively from constructors, track/untrack, reshape/index operations, and APIs such as `image.read`, and are erased at the runtime boundary. Slices are internal views; non-full slices weaken affected extent facts. Source-level value semantics are preserved by copy-on-write detachment on mutation. Integer indexing decreases inferred rank and projects shape facts. `.item()` is the explicit rank-0-to-scalar boundary. `transpose(axis0, axis1)` is a metadata-only shape/stride permutation that preserves storage, offset, and device placement. `reshape` refuses non-contiguous views rather than hiding a copy; `contiguous()` is the explicit materialization boundary. Tensor-to-tensor broadcasting requires equal runtime rank with singleton expansion, while scalar broadcasting is explicit in typed IR.
- Tensor device placement is runtime/compiler metadata, deliberately separate from dtype and shape types. CPU is the default; constructor `gpu = n` and transfer IR nodes preserve explicit placement intent. `.gpu(n)` and `.cpu()` are never erased or hoisted across preceding computation. Runtime tensor storage is a tagged CPU/GPU backing store: CPU tensors own native byte storage, while GPU tensors own a backend buffer handle and are never represented as a populated CPU byte vector. Tensor-to-tensor operations reject mismatched device indices before execution. A GPU operation without a backend kernel fails explicitly instead of materializing a hidden CPU copy. Scalar operands remain ordinary scalar values and can become kernel constants/arguments without being modeled as tensor transfers.
- Union discriminators identify actual alternatives; conversion preserves payloads and remaps tags.
- `error` propagation is explicit through `try`; `none` represents normal absence.
- Exhaustive matching and definite initialization prevent unhandled outcomes and uninitialized reads.
- User-defined classes have statically laid-out fields and methods. Construction may leave fields uninitialized or initialize omitted fields from fresh field-default expressions; the checker tracks field-level initialization.
- Definite initialization uses hierarchical storage paths. Function signatures carry class-return initialization summaries. A shared `StorageEffect` model describes receiver and reference-parameter requirements, writes, guaranteed initialization, and invalidation; const-reference summaries are read-only. At a call boundary, receiver and reference-parameter preconditions are checked against the call-entry state before any of their postconditions are applied, so aliasing cannot let one path's later initialization satisfy another path's read-before-write requirement. This includes aliases between a method receiver and an explicit reference argument. Overlapping postconditions remain conservative when independent summaries cannot prove cross-alias write order. A fixed-point pass propagates these effects across calls before final diagnostics.
- Static proof should erase dynamic safety work whenever the proof is preserved in typed IR. Runtime checks are for facts that genuinely depend on runtime values; they are not a second implementation of facts already proved by the checker. In particular, ordinary initialized local updates stay on scalar SSA/storage paths rather than entering the managed-allocation initialization registry.
- Array-read initialization checks follow the same rule. Lowering carries a conservative `initialization_proven` fact only for arrays known fully initialized by construction or by a proof-preserving value operation. Whole-array read/write reference formation (`T &` through `&array`) drops that fact, while `const T &` formation preserves it because that access path cannot write or replace the array. Control-flow joins keep only facts true on every continuing path. Mutually exclusive `match` cases each start from the same incoming proof state, and the join intersects only continuing cases so a proof from one case can neither leak into another nor be retained unless every reachable continuation establishes it. LLVM may omit the per-element initialization check only while that proof survives. Bounds proof is independent: a statically valid fixed-array constant index, or an index established by a canonical typed-IR loop guard, carries `bounds_proven`; only that explicit fact selects an unchecked address calculation in LLVM. A canonical `for i in range(len(values))` loop whose sole body statement is `values[i] = ...` may establish the same fact when the right-hand side cannot export write authority; partial ranges and more complex loop bodies remain dynamically checked.
- Single inheritance flattens inherited fields and requires explicit `override` for method replacement. Parent and child remain distinct static types; unions represent values that may contain either.
- `super.method(...)` statically resolves the implementation visible through the direct parent while reusing the current compiler-internal receiver.
- Method receivers are compiler-internal; source code has no `self` or `this` binding. Method selection is static rather than dynamically dispatched.
- Class, array, and bin equality is value equality. Class equality is admitted only when the checker proves all compared fields initialized; backend helpers compare fields, elements, or byte contents rather than pointer identity.
- Object identity is not exposed through an `is` operator.
- Top-level statements form the entrypoint.
- Fixed-width numeric conversion separates type compatibility from explicit intent. Already-typed numeric values never change representation implicitly. Contextual numeric literals may be typed directly when representable. Explicit integer-to-floating-point and floating-point-to-floating-point casts may use deterministic IEEE-754 rounding, integer narrowing is range checked, and floating-point to integer conversion requires an explicit rounding operation.
- Call syntax is semantically resolved by the checker into direct function calls, typed function-value calls, built-ins, explicit numeric casts, or constructors before IR lowering. Typed IR does not rediscover call meaning from source names. Capture-free `fn<R>(P...)` values lower to explicit code-address values plus `call.indirect`; the checker has already established the complete signature, and the backend marks address-taken functions for recursion-depth protection because an indirect call can re-enter them. No closure environment is allocated or inferred. Reference metadata preserves whether an explicit `&` path is read/write (`T &`) or read-only (`const T &`) for both parameters and local reference bindings; the LLVM ABI may use the same pointer representation for both without erasing the checked semantic contract. Reference parameters are emitted `nonnull` because source references always denote real addressable storage, and `nocapture` because references are not storable values and cannot escape a call boundary. A `const T &` parameter additionally carries LLVM `readonly` because that access path cannot write. Reference parameters are deliberately not emitted `noalias` or as invariant memory: another `T &` argument may legally alias and mutate the same storage, so those stronger claims would be unsound without a separate proof. Flow-sensitive reference target identity follows the same proof discipline: after `if`/exhaustive `match`, a concrete target is retained only when every continuing path resolves to the same storage. A rebind that can escape a loop is treated as an unknown alias because the loop may execute zero or many times. Unknown aliases conservatively overlap every storage for effect analysis and do not transfer initialization proof to any concrete root; an explicit later rebind restores a precise target.
- Numeric parsing and scalar string conversion lower through typed IR; `print`, `write`, and `input` provide the basic console I/O surface.
- `string` has a runtime representation invariant: valid UTF-8 text with no embedded NUL. External text ingress validates before constructing a string; APIs with typed error channels use them, CLI uses status 2, and host-text APIs without an error case fail deterministically rather than admitting malformed text.
- Standard modules may inject compiler-internal declarations for typed values such as `time.Instant`, `time.Duration`, `random.Generator`, and `process.Result`. These declarations participate in the ordinary class/effect/IR pipeline, while hidden representation fields and constructor rejection keep implementation details out of source semantics.
- Statically known integer division/remainder by zero is rejected before lowering. Remaining integer overflow/division, bounds, allocation-size, range-step, tensor-shape/slice/arithmetic, and numeric cast range checks produce deterministic runtime failures.
- `image` is implemented as a separate native runtime object with PNG/JPEG/BMP/TIFF/WebP codecs. `video` is a separate streaming runtime object backed by FFmpeg; its opaque Reader owns decoder state and yields CPU RGB CHW tensors one frame at a time. Generated LLVM is inspected for actual runtime calls so unused HTTP/image/video objects and external libraries are not linked merely because their declarations exist.

## Interactive compilation

The REPL is a client of the normal compiler pipeline, not a second interpreter or type system. A session retains the text of accepted submissions. A new candidate is appended to that accepted source and compiled through module resolution, generic specialization, the ordinary checker, typed Quidra IR, LLVM IR, and native code generation.

The compiler API `compile_repl_file` also receives the byte boundary between already accepted source and the new submission. Typed IR marks replay of the accepted prefix explicitly. During that prefix, generated native code suppresses `print` and `write` even when they occur through called user functions, so ordinary console effects from an earlier submission are not executed again. The final top-level standalone expression still lowers to `repl.display` and uses the same formatting helpers as compiled programs.

Some accepted state can depend on external or nondeterministic operations whose results cannot yet be reconstructed without executing them again: input, file/environment access, clocks and sleep, random generators, process execution, HTTP, image/video I/O, neural state save/load, CLI argument reads, and `exit`. The REPL computes this conservatively over the typed-IR call graph. Before native execution of a submission that may reach such an effect, the session arms a replay barrier. The barrier remains armed even if that native execution later fails, because an external effect may already have happened before the runtime error. A later native submission is rejected with `REPL_REPLAY_UNSAFE` until `:reset`; compile/link failures do not arm the barrier because no Quidra code ran. This is a correctness barrier, not a claim of true persistent-native incremental execution.

The accumulated-source design therefore preserves semantic identity and recoverability without hiding unsafe replay. Parsing, imports, definite initialization, effects, generics, classes, references, checked arithmetic, equality, diagnostics, and runtime formatting remain shared with ordinary compilation. A future persistent native state / incremental object-link or JIT boundary may remove the conservative replay barrier, but it must preserve these same checked semantics and ownership rules.

## Tooling

The LSP server is a thin client of the ordinary compiler frontend, not a second parser or type system. Unsaved root text is overlaid on the root file while imported modules continue through ordinary module/package resolution. Initial LSP support uses the protocol-default UTF-16 positions, full-document synchronization, push diagnostics, and document formatting. Source byte offsets are converted explicitly to UTF-16 code-unit positions so non-ASCII diagnostics and formatting edits remain protocol-correct. Diagnostics therefore reuse generic expansion, static checking, definite initialization, storage-effect analysis, and import semantics from normal compilation.

The built-in formatter reuses lexer token spans and applies only role-unambiguous whitespace edits. It never rewrites literal contents or comments, and deliberately leaves context-dependent `<`, `>`, and `:` spacing unchanged rather than guessing whether a token is generic/comparison or inheritance/slice syntax. `quidra fmt FILE.qui --check` is the non-writing canonical-form check used by automation. Formatting is idempotent and remains separate from semantic checking.

Source inspection assigns structural identifiers and source hashes and exposes deterministic receiver/reference storage-effect summaries. Sparse authority metadata preserves `const_value`, `read_only_reference`, and `read_write_reference` for bindings, fields, and non-default function parameters, so `--no-source` does not erase const/reference meaning. `--no-source`, `--no-effects`, `--kind`, and `--depth` allow callers to avoid sending repeated or irrelevant data to an LLM. Explicit `parent_id` and `depth` preserve structural hierarchy without span-based reconstruction. With imports, inspection and patching remain scoped to the requested root file: imported declarations participate in semantic checking and native compilation but are not exposed as editable nodes of the root source. Patching validates a base revision and expected node hashes before applying changes, then checks the resulting file-aware program. Parser changes must preserve spans for these tools. Recursive type lookahead shares the same bounded nesting policy as full parsing, and statement-level recovery may report multiple independent diagnostics without treating recovered malformed nodes as valid AST.

## Runtime representation and lifetime policy

GPU devices use one process-wide zero-based Quidra index space. The device layer owns enumeration, allocation, release, explicit copies, runtime kernel compilation/loading and launch. On Linux/Windows NVIDIA, the runtime dynamically loads the NVIDIA Driver API supplied by the installed driver; it does not discover or invoke a user CUDA Toolkit, `nvcc`, `CUDA_HOME`, or `/usr/local/cuda`. WSL therefore uses the Windows-provided NVIDIA driver interface exposed into WSL rather than installing a second Linux kernel driver. On macOS, allocation, copies and compute use Metal. On AMD, Quidra dynamically uses the HIP runtime and HIP runtime compilation facilities when a compatible ROCm/HIP installation is present; the source-level `gpu = n` contract is unchanged. Backend identity is tied to the Quidra release. Unsupported backend/dtype/operation combinations are explicit errors, never CPU fallbacks. DNN-specific acceleration such as cuDNN/cuBLAS/NCCL belongs to the DNN package rather than core. NVIDIA and AMD device compute support both Quidra `float32` and `float`/`float64` where the backend primitive exists, plus the built-in integer tensor dtypes with checked integer semantics. Metal compute supports the built-in integer dtypes and `float32`; Apple GPU Metal kernels do not provide Quidra's IEEE-754 binary64 compute contract, so `float`/`float64` tensors may be placed and explicitly copied on Metal devices but a compute operation that requires FP64 fails explicitly rather than narrowing to `float32` or falling back to CPU.

Dense, fully initialized contiguous CPU floating-point tensors use a validated linear-algebra fast path: initialization/layout/storage-range checks are hoisted before the numeric loop, the kernels read validated contiguous TensorStorage bytes directly instead of materializing left/right dense copies, and matrix multiplication iterates columns innermost while preserving each output element's original accumulation order. Integer linear algebra stays on checked multiply/add paths so optimization cannot introduce silent overflow or UB. Neural graph storage and forward/backward kernels are dtype-specialized: float32 graph values and gradients stay in native `float` arithmetic rather than being promoted through a hidden double graph, while float64 uses `double`. Generic second-moment update state intentionally uses double precision before the final Parameter write rounds to its declared dtype.

The semantic copy rule is centralized through a value-storage policy: direct scalar values copy directly, immutable values may share storage, and independently mutable aggregate values clone whenever independent ownership is required. For direct calls, the IR may internally borrow an ordinary by-value aggregate parameter when a conservative whole-body analysis proves that the callee neither mutates that parameter nor exposes it through writable storage. This is an unobservable optimization of ordinary value passing; it is distinct from the explicit source-level `const T &` contract, which intentionally exposes shared storage as a live read-only access path. Heap-backed runtime values use deterministic managed ownership with explicit retain/release operations in typed IR and generated LLVM. Safe references pin the containing managed allocation so an observable `&storage` remains valid even if the original owning binding is reassigned; rebinding or leaving the reference scope unpins it.

Runtime and standard-library calls borrow their operands for the duration of the call unless a result explicitly retains, clones, or otherwise takes ownership. Owned expression temporaries are released after their last use, including discarded expressions and intermediate text values. Composite drop helpers recursively release managed fields, array elements, and union payloads. JSON and HTTP wrappers provide explicit drop/clone hooks for their external C++ state.

This is intentionally an implementation boundary: copy-on-write, moves, retain/release elision, or a cheaper ownership representation may replace eager cloning and the current managed-allocation registry when observable `=` and `&` behavior remains identical.

Sanitizer development builds propagate AddressSanitizer/UndefinedBehaviorSanitizer instrumentation to generated native programs as well as the compiler. This lets CI exercise generated retain/release, pin/unpin, bounds, and drop paths under the same memory-safety instrumentation instead of sanitizing only the compiler process.

## Future work

External-resource effects, concurrency, optional vendor accelerator libraries, broader real-hardware GPU coverage, contracts and verification evidence, a mature standard library/package distribution model, WASM, self-hosting, richer class polymorphism, and further runtime ownership/copy-elision optimizations remain development areas. Tensor copy-on-write and explicit CPU/GPU placement/transfer boundaries are already implemented as semantic/runtime contracts. Features should add meaningful intent, preserve clear static contracts, and be validated against real human and LLM editing tasks.


## C FFI boundary

External C declarations remain explicit in the checked program and typed IR. They are not emitted as Quidra function bodies: LLVM receives a typed `declare` for the exact C symbol and call sites target that symbol directly. Results remain ABI-stable by-value scalars or `void`, and scalar parameters remain by value. Managed `string` and `bin` inputs are represented in the checked program and typed IR as explicit `const T &` read-authority borrows; only at the C ABI boundary does lowering load the referenced managed value and expand it to an adjacent `(const data pointer, uint64 byte length)` pair. The backend therefore consumes resolved authority/lifetime information instead of rediscovering borrowing from a source name or pointer shape. Mutable references, hidden by-value managed borrows, arbitrary managed aggregates, defaults, generics, and ownership-bearing foreign results remain rejected. The generated `main` entrypoint, the compiler-owned `n_*` function-mangling namespace, the implementation-owned `quidra_*` / `__quidra_*` symbol namespaces, and runtime-prelude C symbols cannot be rebound through source `extern` declarations, avoiding conflicting foreign prototypes and future runtime-name collisions. The checker also enforces one source declaration per external C symbol across the complete checked program, so duplicate aliases fail before LLVM declaration emission. This keeps ownership, lifetime, text encoding, initialization, and alias semantics from being guessed across foreign code. External calls conservatively arm the REPL replay barrier.


Declaration-only REPL submissions (functions, classes, and imports with no top-level executable statement) take a non-executing incremental path: the complete candidate is validated by the ordinary file-aware checker, then accepted without LLVM generation, native linking, or process execution. This remains safe after an external-effect replay barrier because no runtime state is reconstructed. Executable submissions still use accumulated-source reconstruction until a persistent runtime-state ABI can preserve bindings, references, managed ownership, imports, generics, and definite-initialization facts without changing language semantics.

## Native runtime boundary

Generated programs are still lowered directly from typed Quidra IR to LLVM IR. Native executables additionally link a small platform static runtime archive through a C ABI (`libquidra_runtime.a` on Unix-like hosts and `quidra_runtime.lib` on Windows). The runtime is for operating-system and standard-library facilities that should not be duplicated as emitted LLVM text; it is not a source transpilation layer and does not interpret Quidra.

The generated entry point uses the platform `main(argc, argv)` ABI and records those arguments in the runtime before executing the ordinary lowered top-level program. This keeps command-line access available to the standard `cli` module without giving source programs raw pointer access.

The compiler and REPL share the same native linker helper and runtime-library discovery rules. Linux locates the compiler executable through `/proc/self/exe`, macOS through the Mach-O executable-path API, and Windows through `GetModuleFileNameW`. Development builds find the runtime beside the `quidra` executable; installed builds find it under `lib/quidra`. `QUIDRA_RUNTIME_LIBRARY` may explicitly select a runtime archive for nonstandard layouts. Native compiler/linker launches and source-level process execution both use host process APIs: POSIX uses `fork/exec`, while Windows uses `CreateProcessW`. No shell is inserted to reinterpret executable names or arguments.
